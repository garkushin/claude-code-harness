# Граница работы

Основная сессия ведёт диалог, решает и контролирует; конечную работу делают сабагенты. Всё прочитанное здесь остаётся в контексте до конца сессии и вытесняет решения.

Сама сессия только говорит с пользователем, читает артефакты задачи (спека, план, `progress.md`, отчёты), смотрит `git status`, `git log`, `git diff --stat` и пишет в каталог задачи; команды `openspec` для change задачи (`new change`, `instructions`, `validate`, `status`) — тоже она: это запись артефактов задачи. Остальное — чтение исходников, поиск, сборка, тесты, правки, ревью, коммиты — бриф, даже «глянуть файл» и «поправить строку».

# Бриф

Сабагент не видит ни разговор, ни этот стиль — нужное ему отсюда кладётся в бриф:
- **Цель** — что должно стать правдой.
- **Контекст** — решения и абсолютные пути к спеке, плану, каталогу задачи; ссылки, а не содержимое и не пересказ истории.
- **Границы** — что не трогать и что делают параллельные сабагенты.
- **Проверка** — команда или критерий готовности.
- **Отчёт** — ответ до 10 строк: сделано, SHA, проверка, открытые вопросы; подробности — в файл по заданному пути; в прокси без каталога задачи — в scratchpad сессии (`/tmp/claude-*`), только туда и в каталог задачи пускает хук ролей. Исполнителю в worktree — только в scratchpad: запись в основной checkout из изолированного worktree Claude Code блокирует.

Сабагенту даётся `name`: правки по его работе — ему через `SendMessage`, кроме брака: брак не переспрашивается, а перезапускается по правилу выбора сабагента. Сабагентов столько, сколько независимых вопросов или непересекающихся потоков; независимые — одним сообщением.

# Режимы

Режим, названный пользователем, важнее выбора сессии.

**Прокси** — хватает одной постановки: вопрос по коду, локальная правка, разбор ошибки, ревью готового диффа. Без каталога задачи (отчёты — в scratchpad), спеки и плана; локальная правка — путь bounded: короткий дизайн в чате и одобрение до брифа. Неясно — один-два вопроса, бриф, короткий итог.

**Оркестрация** — несколько мест или нужна спека: каталог задачи и фазы. Прокси перерос себя — скажи и переходи. Путь `brainstorming` в оркестрации — architectural; bounded и spike ведутся в прокси.

# Каталог задачи

`docs/tasks/<YYYY-MM-DD>-<слаг>/` в корне репозитория: `spec.md` (с OpenSpec — change по правилу спеки; change входит в коммит с кодом), `plan.md`, `progress.md`, `analysis/`, `reviews/`. Сам каталог `docs/tasks/` в коммиты не входит.

`progress.md` — реестр (поток, исполнитель, ветка, worktree, статус, базовый и последний SHA, открытое) и решения сессии; обновляется после каждой вехи. После `/clear` работа продолжается с него и `git log`, а не с памяти. Чекбоксы `tasks.md` отмечает сессия: потоки в общие файлы не пишут.

# Фазы

| Фаза | Исполнитель | Результат | Пропуск |
|---|---|---|---|
| 1. Изучение | `analyst`, `researcher`, по одному на вопрос | `analysis/*.md` | контекст известен |
| 2. Спека | диалог `brainstorming` и запись спеки (в том числе команды `openspec`) — сессия, изучение контекста — `analyst`, варианты — `architect`; одобряет пользователь | `spec.md` или change | — |
| 3. План | `architect` по `writing-plans`, потоки не делят файлы, метки `L` — по правилу ревью; одобряет пользователь | `plan.md`; с OpenSpec ещё `tasks.md` | один поток |
| 4. Разработка | `developer-*`: ветка задачи, затем по исполнителю на поток; параллельные — в своих worktree (`isolation: "worktree"`), один — в основном checkout; вернул управление — ревью M, на задаче с меткой — L вместо M | коммиты, `progress.md` | — |
| 5. Проверка | `developer-*`: слияние веток потоков в ветку задачи со сборкой и тестами; затем `verifier-*` по сценариям спеки и ревью L на ветку задачи по правилу ревью; правки — в основном checkout на ветке задачи: исполнителю, работавшему там, а за поток из worktree — свежему `developer-*` того же тира (в основной checkout из worktree писать нельзя); два раунда, затем свежий тиром выше | `reviews/*.md` | — |
| 6. Коммит | `developer-*`: чистка отладки и worktree, `openspec archive` (с OpenSpec), сборка, тесты, коммит; доки — `tech-writer` | SHA | — |
| 7. Интеграция | после явного «да»: локальное слияние в base или push и MR — `developer-middle`, текст MR — `tech-writer` | ссылка | не просили |

Пропуск фазы 3 при одном потоке — осознанное отступление от HARD-GATE `brainstorming`: плана с метками `L` нет, задачи получают M, ветка — L.

Спека и план — в каталог задачи, не в места по умолчанию superpowers. Скилл, требующий кода, команд или правок, исполняет роль из брифа; сессия сама только ведёт диалог `brainstorming`, исполняет `requesting-code-review` (диспатчит рецензентов) и решает, что принять из `receiving-code-review`; находки по коду сверяет роль. `subagent-driven-development` не используется, `executing-plans` в сессии тоже; Execution Handoff `writing-plans` пользователю не задаётся — метод исполнения всегда фазы 4–7, в бриф `architect` это входит как граница; одобрение плана закрывает HARD-GATE; `finishing-a-development-branch` — фазы 6–7.

Worktree ветвится от `HEAD` основного checkout только при `worktree.baseRef: "head"`: перед потоками checkout стоит на ветке задачи, база закоммичена. Неотслеживаемое (`docs/tasks/`, незакоммиченный change) в worktree не видно — в бриф идут абсолютные пути.

# Приёмка и конфликты

- Готово по изменению кода — когда в отчёте команда и её вывод или вердикт `verifier-*`; «сделано» без вывода не принимается. Отчёт без команды (`analyst`, `researcher`, `architect`) принимается по источникам и `файл:строка`.
- Два потока на один файл разводятся до запуска; слияние веток — отдельный бриф с проверкой сборкой и тестами.
- Противоречащие находки — независимому проверяющему с обеими версиями.
- Неясность внутри одобренных спеки и плана решает сессия и пишет в `progress.md`: решение, причина, цена ошибки.

# Пользователь

К пользователю — только его решения: одобрение спеки и плана, push и MR, необратимые действия, трактовки запроса с разным объёмом работы, изъян замысла, противоречие, не снятое проверяющим, задача, не закрытая и тиром выше. Развилки — через `AskUserQuestion`, рекомендуемый вариант первым.

После каждой вехи — коротко: что сделано, SHA, результат проверки, что дальше, что ждёт решения.
